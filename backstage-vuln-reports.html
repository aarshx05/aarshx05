H4: Path Traversal + Remote Code Execution in fetch:rails Scaffolder Action

Component: @backstage/plugin-scaffolder-backend-module-rails CWE-22, CWE-94

Summary

The fetch:rails scaffolder action concatenates user-controlled input (values.name) into a filesystem path without sanitization, allowing path traversal. Combined with the --template flag (which accepts a URL pointing to arbitrary Ruby code), this gives any template user full remote code execution on the Backstage backend server.

Why This Should Be Accepted

4 independent signals confirm this is a real, reportable vulnerability:

1. Violates their own SECURITY.md — Backstage's threat model says template authors are trusted, but template users filling in form values are not. This bug lets a user (not an author) achieve RCE.

2. Sibling actions already fixed — fetch:template uses resolveSafeChildPath(). The Rails module does not.

3. ESLint rule exists but missed this module — Backstage has a custom lint rule to flag unsafe path construction. It doesn't cover scaffolder-backend-module-rails.

4. Previous CVE for same class — CVE-2024-26150 fixed path traversal in a different scaffolder action, proving they treat this class as a security issue.

Vulnerable Code

1. Unsanitized path concatenation

railsNewRunner.ts:71 — name comes directly from user form input:

const { name, imageName, railsArguments } = values;  // line 49
// ...
`${intermediateDir}${path.sep}${name}`,               // line 71 — UNSANITIZED

No resolveSafeChildPath(), no regex, no character filter. Compare with fetch:template which does use resolveSafeChildPath().

2. Template URL passes through unsanitized

railsArgumentResolver.ts:149-157:

if (options?.template) {
  argumentsToRun.push('--template');
  argumentsToRun.push(
    options.template.replace(`.${separatorPath}`, `${projectRoot}${...}`)
  );
}

The .replace() only handles ./ prefix. Absolute paths and URLs pass through unchanged. Rails --template accepts URLs and executes them as Ruby.

3. Raw process spawn, no sandbox

executeShellCommand.ts:59:

const process = spawn(command, args, spawnOptions);

Node.js child_process.spawn — runs with the Backstage backend's full OS privileges.

4. Schema accepts any string

index.ts:73: name: z.string() — no validation.

index.ts:136-141: template: z.string({ description: 'can be a filesystem path or URL' }).

M1: OIDC Provider Accepts PKCE Plain Method, Defeating PKCE Protection

Component: @backstage/plugin-auth-backend CWE-327 (Use of Broken Crypto Algorithm)

Summary

Backstage's built-in OIDC provider (OidcService.ts) accepts code_challenge_method: "plain" for PKCE, advertises it in the discovery document, and silently defaults to it when the method is omitted. With plain, the code_challenge equals the code_verifier—it appears in the authorization URL, which is visible in browser history, server logs, proxies, and referrer headers. Anyone who sees the URL can exchange an intercepted authorization code for tokens, completely defeating PKCE.

Why This Should Be Accepted

Direct RFC violation with concrete exploit path:

1. RFC 9700 Section 2.1.1 (OAuth Security BCP): "Authorization servers MUST support PKCE... and MUST NOT support the plain challenge method."

2. Discovery doc actively advertises it — code_challenge_methods_supported: ["S256", "plain"] tells clients that plain is acceptable.

3. Silent downgrade — verifyPkce() treats any falsy method (undefined, null, empty string) as plain, so a client that omits the method silently loses PKCE protection.

Vulnerable Code

1. Discovery document advertises plain

OidcService.ts:236:

code_challenge_methods_supported: ['S256', 'plain'],

2. Authorization accepts plain challenges

OidcService.ts:339-345:

if (codeChallenge) {
  if (
    !codeChallengeMethod ||
    !['S256', 'plain'].includes(codeChallengeMethod)  // accepts 'plain'
  ) {
    throw new InputError('Invalid code_challenge_method');
  }
}

3. Token exchange does plain comparison

OidcService.ts:774-792 — the verifyPkce method:

private verifyPkce(opts) {
  if (!opts.method || opts.method === 'plain') {       // THE BUG
    return opts.codeChallenge === opts.codeVerifier;   // no hashing!
  }
  if (opts.method === 'S256') {
    const hash = crypto.createHash('sha256')
      .update(opts.codeVerifier).digest('base64url');
    return opts.codeChallenge === hash;
  }
  return false;
}

Line 779: !opts.method means undefined/null/empty all fall through to plain comparison.

M4: Unbounded Memory Consumption in URL Readers via getRawBody Without Limit

Component: @backstage/backend-defaults (urlReader) CWE-770 (Allocation Without Limits)

Summary

Every URL reader in Backstage calls getRawBody(stream) without a limit option. The raw-body package supports { limit: '10mb' } to cap memory consumption, but Backstage never passes it. A single malicious URL that streams infinite data exhausts the Node.js process memory and crashes the backend. If the URL is registered as a catalog location, it persists in the database and crashes the backend again on every restart, creating a denial-of-service crash loop.

Why This Should Be Accepted

The fix exists in the library but is never used:

1. raw-body supports limit — adding { limit: '50mb' } would completely prevent this. Backstage never passes it.

2. Single request, full crash — one URL consumes the entire Node.js heap. No rate limiting helps.

3. Persistent crash loop — catalog locations are stored in the database. The backend re-reads them on restart, crashing again.

4. 5 vulnerable call sites — this isn't a single oversight; every getRawBody call in the codebase is missing the limit.

Vulnerable Code

1. Central factory — all URL readers flow through here

ReadUrlResponseFactory.ts:54:

buffer = getRawBody(stream);  // NO limit — consumes entire response

Used by every URL reader: GitHub, GitLab, Bitbucket, Azure, AWS S3, GCS, Gerrit, Gitea, Harness, and the generic FetchUrlReader.

2. Additional direct calls (also missing limit)

FileLineContext
GoogleGcsUrlReader.ts122GCS file reads
ReadableArrayResponse.ts66Tree response file content
GcpBucketWorkspaceProvider.ts124, 133Scaffolder workspace rehydration
