Filter applied: For each of the 57 confirmed findings, we asked: Can an external attacker exploit this against a responsibly-configured Backstage instance without the operator first shooting themselves in the foot? Findings were eliminated if they require the victim to opt into a "dangerously" prefixed flag, depend on operator misconfiguration where the default is safe, require pre-existing access that makes the finding redundant, are not currently exploitable, rely on trusted-author trust boundaries working as designed, or are deployment/infrastructure concerns rather than code vulnerabilities.
What "responsibly configured" means: Default Backstage deployment. No dangerously* flags enabled. backend.reading.allow set to specific SCM hosts (no reckless wildcards). Standard auth. Permission system may or may not be enabled (default is off, which is the operator's call). Behind standard corporate network or public with auth. Template actions installed from known sources.

The 7 That Survive

Genuine code-level issues an attacker could hit without operator self-sabotage

Bottom line: Of 57 confirmed true positives, only 7 represent genuine code-level security issues exploitable against a properly-configured instance. The remaining 50 are by-design behaviors with explicit opt-in, operator misconfiguration prerequisites, defense-in-depth observations, or minor information disclosures with no actionable impact. The 7 survivors are: one real community-module bug (H4), three protocol/implementation weaknesses (M1, M3, M4), one least-privilege design gap (H2), one systemic design limitation (M11), and one minor DoS vector (L12). None are remotely exploitable without authentication, and none lead to RCE or data breach on a default deployment.
