SD-009 Mass Source Deanonymization via Memory Dump Critical
Threat Model
Attacker: A state actor who gains read access to the SecureDrop server's process memory (via /proc/pid/mem, core dump, cold boot attack, or compromised admin running gdb).
Goal: Recover the passphrase → filesystem_id mapping for ALL sources who have logged in since the last server restart, enabling mass deanonymization.
Attack Chain
  1. Attacker gains read access to Apache/mod_wsgi process memory
  2. Locates the _SourceScryptManager singleton on the heap
  3. The singleton's two @lru_cache dictionaries contain every derivation since restart
  4. derive_source_gpg_secret: passphrase → gpg_secret
  5. derive_source_filesystem_id: passphrase → filesystem_id
  6. Attacker dumps the cache — every source since restart is exposed
  7. filesystem_id maps directly to the source's directory on disk and DB records
Vulnerable Code
# source_user.py:155-180 @lru_cache # noqa: B019 ← NO maxsize, Bandit warning SUPPRESSED def derive_source_gpg_secret(self, source_passphrase): scrypt_for_gpg_secret = scrypt.Scrypt(length=64, salt=self._salt_for_gpg_secret, ...) return b32encode(scrypt_for_gpg_secret.derive(source_passphrase.encode("utf-8"))) @lru_cache # noqa: B019 ← NO maxsize, Bandit warning SUPPRESSED def derive_source_filesystem_id(self, source_passphrase): scrypt_for_filesystem_id = scrypt.Scrypt(length=64, salt=self._salt_for_filesystem_id, ...) return b32encode(scrypt_for_filesystem_id.derive(source_passphrase.encode("utf-8")))
Live Proof

Impact:
  • Single memory dump deanonymizes ALL active sources since last restart
  • Cache maps passphrase → filesystem_id (links anonymous submissions to passphrases)
  • Unbounded growth → eventual OOM crash (DoS)
  • Fix: one parameter — @lru_cache(maxsize=128)
BugCrowd: Not excluded. No pre-existing issue. Falls under "Extraction of private key material / source identity." The # noqa: B019 shows the team suppressed the lint warning without addressing the security implication. Est. reward: P2 $1,000–$1,500. Acceptance: ~75%.
SD-007 2FA Token Oracle via Exception Distinguishability Critical
Threat Model
Attacker: An adversary who has obtained a journalist's username and the ATHS token for the journalist interface. They do NOT know the password or 2FA secret.
Goal: Discover valid TOTP/HOTP codes independently, splitting 3-factor auth into two separate attacks.
Attack Chain
  1. Send: username='journalist1', token='000000', password='anything'
  2. Server calls verify_2fa_token('000000') FIRST → OtpTokenInvalid
  3. Attacker learns: token '000000' is wrong (never reached password check)
  4. Send: username='journalist1', token='123456', password='anything'
  5. Server calls verify_2fa_token('123456') → PASSES
  6. Server stores last_token = '123456', commits to DB (token consumed!)
  7. Server calls valid_password('anything') → WrongPasswordException
  8. DIFFERENT exception → attacker knows token '123456' IS VALID
  9. Now brute-force the password separately with known-valid tokens
Vulnerable Code
# models.py:842-849 sanitized_token = user.verify_2fa_token(token) ← 2FA FIRST user.last_token = sanitized_token ← stored BEFORE password check db.session.commit() if not user.valid_password(password): ← password SECOND raise WrongPasswordException("invalid password")

SD-031 Cross-Source File Leak via Reversed Substring Match High
Threat Model
Attacker: A malicious or buggy component calling path_without_filesystem_id() with a crafted filename. Could be triggered through the journalist API or any code path resolving files without a filesystem_id.
Goal: Access files belonging to a DIFFERENT source by exploiting the reversed substring check.
Attack Chain
  1. Attacker knows or guesses filenames in the store
  2. Crafts a query containing multiple real filenames as substrings
  3. Bug: file_ in filename checks if DISK name is substring of QUERY
  4. All files whose names are substrings of the query are matched
  5. Files from different sources match → cross-source data leak
Vulnerable Code
# store.py:174 if file_ in filename: ← REVERSED! Should be file_ == filename joined_paths.append(os.path.join(rootdir, file_))
Live Proof
MATCHExact filename → correct result (baseline)
MISMATCHTwo filenames from same source → buggy returns 2 files, correct returns 0
CROSS-SOURCEFilenames from Source A + Source B → returns files from BOTH sources
Impact:
  • Cross-source file access — Source A's files returned for Source B's query
  • Violates source isolation boundary — core security invariant
  • TooManyFilesException on legitimate queries (DoS)
  • Fix: change file_ in filename to file_ == filename
BugCrowd: Not excluded. No pre-existing issue. Unambiguous code bug (not a design decision). Est. reward: P3 $500–$750. Acceptance: ~70%.

Threat Model
Attacker: State-level adversary with server access or Tor-level MITM capability.
Goal: Forge journalist replies to a source — false meeting locations, distrust injection, or identity exposure.
Attack Chain
  1. Journalist writes reply: "Meet me at Central Park, 3pm Tuesday"
  2. Server encrypts with source's public key
