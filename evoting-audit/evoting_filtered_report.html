SP-047 SECURITY_LEVEL Environment Variable — Complete Crypto Collapse CRITICAL
Source (commit: latest master)
crypto-primitives/src/main/java/.../internal/securitylevel/SecurityLevelConfig.java:33-38
public static SecurityLevelInternal getSystemSecurityLevel() {
    final String securityLevelValue = System.getenv("SECURITY_LEVEL");
    if (securityLevelValue == null) {
        return SecurityLevelInternal.STANDARD;
    }
    return SecurityLevelInternal.valueOf(securityLevelValue);
}
Attack Scenario (C.5.2 compliant)

Entry point: Environment variable SECURITY_LEVEL on any component using crypto-primitives

Malicious party: Infrastructure operator, supply-chain attacker, or attacker with container escape

Code path: SecurityLevelConfig.getSystemSecurityLevel() → SecurityLevelInternal.valueOf("TESTING_ONLY") → all downstream crypto uses 16-bit security (48-bit modulus) instead of 128-bit (3072-bit)

No mitigation found: No runtime guard, assertion, startup check, or production environment validation exists anywhere in the codebase. Grep for TESTING_ONLY and SECURITY_LEVEL across all repos confirms no validation.

Concrete Impact
Technical: All ElGamal encryption drops to 48-bit modulus (factorable in milliseconds). All ZKPs, Bayer-Groth shuffle proofs, and Pedersen commitments provide zero security.
Business: An attacker can decrypt all votes, forge proofs of correct shuffling, and manipulate the election tally — all while the verification system reports success (proofs verify trivially at 16-bit security).
Protocol impact: Complete bypass of universal verifiability. Manipulation goes undetected by voter AND system.

SP-032 Keystore Password Zeroed with '0' (0x30) Not '\0' (0x00) HIGH
Source
crypto-primitives/src/main/java/.../internal/signing/SignatureKeystoreService.java:88
} finally {
    Arrays.fill(password, '0');  // BUG: '0' = char 0x30, not '\0' = 0x00
}
Attack Scenario

Entry point: Memory access (heap dump, core dump, cold boot, debugger attachment)

Code path: Keystore password loaded → used for signing operations → Arrays.fill(password, '0') leaves "000000..." in memory instead of null bytes

Concrete impact: Password length leaked (visible as run of 0x30 bytes). Password location trivially identifiable in heap. Correct zeroing ('\0') would appear as empty memory, indistinguishable from uninitialized space.

PoC
char[] password = "Election2025!Secret".toCharArray();
Arrays.fill(password, '0');  // What the code does (buggy)
// Memory: 0x30 0x30 0x30 0x30 0x30 ... (19 bytes of '0')
// Leaks: password was 19 chars long, located HERE

Arrays.fill(password, '\0'); // What it should do
// Memory: 0x00 0x00 0x00 0x00 0x00 ... (empty)

This is a clear code bug (not a best practice recommendation per C.5.4). The code attempts to zero the password but uses the wrong character. The fix is a single character change: '0' → '\0'.

SP-006 Year-of-Birth Authentication Challenge — 6.6 Bits Entropy MEDIUM
Source
voter-portal/apps/voter-portal/src/assets/i18n/EN.json:74
"startvoting.enteryob": "Enter your year of birth"
VerificationCardStateEntity.java:96
checkArgument(authenticationAttempts > 0 && authenticationAttempts <= MAX_AUTHENTICATION_ATTEMPTS) — MAX = 5
Attack Scenario

Precondition: Attacker has stolen a voter's Start Voting Key (SVK) / voting card

Challenge mode: YOB (year of birth) — one of three supported modes (DOB, YOB, eGov token)

Attack: Enumerate ~100 possible birth years (1924–2024). With 5 attempts and demographic knowledge:

Statistical Analysis
YOB mode: ~100 possible values, 5 attempts allowed
Base success rate: 1-(99/100)^5 = 4.9%

With demographic knowledge (age 40-50):
  10 possible values, 5 attempts → 1-(9/10)^5 = 41%

With demographic knowledge (age 30-55):
  25 possible values, 5 attempts → 1-(24/25)^5 = 18.5%

DOB mode: ~36,500 values → negligible risk
eGov token: high entropy → not affected
Mitigating Factors

The authentication sends a derived hash (256-bit, derivedAuthenticationChallenge per the JSON schema), not the raw year. The attacker needs the SVK's keying material to compute the hash. The card is permanently blocked after MAX_AUTHENTICATION_ATTEMPTS failures.

Despite the hashing, the fundamental entropy of the input remains ~6.6 bits (100 values). An attacker with the SVK can offline-enumerate all 100 hashed values.

Disproved SP-007/008, SP-022, SP-035, SP-042/043, SP-033 CODE VERIFIED FP

SP-007/008 (Return code linkability / vote deanonymization): Source code analysis disproved. shortChoiceReturnCodes are opaque random tokens — the mapping from return code to actual vote choice exists only on the voter's physical voting card and in the SDM (Secure Data Manager), NOT in the voting server database. A DB insider sees return codes linked to voter identity but cannot map them back to candidates without the voter's card. The protocol's trust model explicitly distributes this knowledge across control components. At most this leaks participation metadata (who voted), not how they voted. Not a vote privacy breach.

SP-022 (DUMMY_ELECTION_EVENT bypass): Code analysis disproved. ConfigureVoterPortalService.java:52 has checkArgument(!DUMMY_ELECTION_EVENT_ID.equals(electionEventId)) blocking writes. GET endpoint returns static dummy config from file. This is a deliberate deployment-test feature, not a bypass.

SP-035 (unbounded confirmation attempts): Code has MAX_CONFIRMATION_ATTEMPTS = 5 enforced by checkState().

SP-042/043 (AEAD empty AD): Keys are derived per-voter-per-election-per-choice via KDF(hash(pC_id_k, vc_id, ee, tau_k), ...). Cross-context replay fails because keys differ. Best practice observation, not exploitable.

SP-033 (JDWP debug ports): Found only in evoting-e2e-dev/docker-compose/docker-compose.common.yml. This is a development environment configuration, not production code.
