Executive Summary

A comprehensive sweep of the Swiss Post e-voting codebase (~66MB, 1,369+ Java files, JavaScript crypto libraries, control components, and DevOps configurations) identified one concrete code-level vulnerability in the inter-service request authentication mechanism and one cryptographic design concern in the ElGamal key deserialization path.

The primary finding — URL omission from inter-service request signatures — is a real, demonstrable bug with a working PoC. All other attack surfaces examined (SQL injection, XSS, deserialization, RNG, vote encryption, ZKP verification, mixnet, certificate validation) were found to be properly implemented.

Finding: Inter-Service Signature URL Omission

HIGH Cross-Endpoint Signature Replay Attack

Vulnerability

SignedRequestContent.getBytes() computes the signature hash over method + body + originator but never includes the URL, even though the URL is passed to the constructor and stored as a field. Both the signing path (RequestSigner.sign()) and the verification path (RequestVerifier.verifySignature()) use this method.

SignedRequestContent.java:59-68 • RequestSigner.java:26 • RequestVerifier.java:29

Affected Code

// SignedRequestContent.java — URL stored but NEVER used in getBytes()
public SignedRequestContent(String url, String method, String body, String originator) {
    this.url = url;       // <-- stored
    this.method = method;
    this.body = body;
    this.originator = originator;
}

public byte[] getBytes() {
    StringBuilder sb = new StringBuilder();
    if (StringUtils.isEmpty(body)) {
        return sb.append(method).append(originator)       // <-- NO URL
                 .toString().getBytes(UTF_8);
    } else {
        return sb.append(method).append(body)             // <-- NO URL
                 .append(originator).toString().getBytes(UTF_8);
    }
}

Impact Analysis

GET requests: All signed GET requests from the same NodeIdentifier produce identical signatures because GET has no body. The signature is simply RSA_Sign(SHA256("GET" + nodeIdentifier)). Capturing one signed GET gives a universal credential for every secured GET endpoint.

POST/PUT requests: The body IS included, so cross-endpoint replay requires matching body content. Still allows replaying a provisioning POST to one service's tenantdata endpoint against another service's tenantdata endpoint.

No replay protection: No nonce or timestamp is included in the signature. Captured signatures never expire.

All 9 voting server services apply SignedRequestFilter for URLs matching .*secured.*|.*platformdata.*|.*tenantdata.*:

Concrete Attack Scenario

ATTACKER MODEL: Network position between internal services
(Per Swiss Post attacker model: "Attacker can read, modify,
 replay messages sent between components of the system")

1. MITM between Orchestrator and any service
2. Capture ONE legitimate signed GET request:
   GET /orchestrator/mixdec/secured/tenant/T/electionevent/E/ballotbox/B
   Headers:
     Originator: ORCHESTRATOR
     Signature: <base64-signature>

3. Replay to election-information:
   GET /election-information/secured/tenant/T/electionevent/E/ballotbox/B2
   Headers:
     Originator: ORCHESTRATOR          (same)
     Signature: <base64-signature>     (same — URL not in signature)

4. SignedRequestFilter passes because:
   hash("GET" + "ORCHESTRATOR") matches on BOTH endpoints

5. Request proceeds to export encrypted ballot box data

PoC

Working PoC at evoting-audit/poc/cross-endpoint-signature-replay-poc.py demonstrates that getBytes() produces identical output regardless of URL for the same method and originator.

Recommended Fix

public byte[] getBytes() {
    StringBuilder sb = new StringBuilder();
    sb.append(url);           // ADD: bind signature to endpoint
    sb.append(method);
    if (!StringUtils.isEmpty(body)) {
        sb.append(body);
    }
    sb.append(originator);
    sb.append(nonce);         // ADD: replay protection
    return sb.toString().getBytes(StandardCharsets.UTF_8);
}

Finding: ElGamalPublicKey Missing Group Membership Check

MEDIUM Missing Subgroup Membership Validation on Deserialization

ElGamalPublicKey (in the legacy cryptolib) skips group membership checks when constructing from deserialized elements. The constructor validates that values are in [1, p-1] but does not verify v^q mod p == 1 (actual subgroup membership).

ElGamalPublicKey.java:42-43 • ZpGroupElement.java:85-93

// ElGamalPublicKey.java — documented performance shortcut
/**
 * Note: For performance reasons, a group membership check is not performed
 * for any Zp group element in the specified list. Therefore, this membership
 * should be ensured prior to specifying the list as input to this constructor.
 */
public ElGamalPublicKey(List<ZpGroupElement> elements, ZpSubgroup zpSubgroup)

// ZpGroupElement.java — validates range but NOT subgroup membership
private static void validateInput(BigInteger value, BigInteger p, BigInteger q) {
    Validate.inRange(value, BigInteger.ONE, pMinusOne, ...);
    // MISSING: value.modPow(q, p).equals(BigInteger.ONE)
}

Impact Assessment

If an attacker can inject a malicious public key element that is in [1, p-1] but NOT in the subgroup of order q, small-subgroup attacks could potentially leak information about secret exponents. However:

  • The comment states membership "should be ensured prior" — callers may validate externally
  • The newer crypto-primitives library (used by control components) has separate GqElement with proper factory methods
  • Injecting a malicious public key requires compromising the key provisioning chain, which is signed by the admin board

This is a defense-in-depth concern rather than a directly exploitable vulnerability with the current architecture.

Bounty Eligibility Assessment

Assessment: Borderline Bounty-Worthy

The URL omission finding is a real code bug with a working PoC in a security-critical authentication mechanism. It is explicitly within the attacker model (network position between components). However, its direct impact on the special bounty categories is limited:

For Special Bounties

CategoryBountyDoes This Finding Qualify?
Individual vote manipulation €70k–230k No. Cross-endpoint GET replay cannot directly manipulate votes (POST body would need to match a valid vote structure)
Voting privacy on server €40k–50k No. Exported ballot box data is encrypted; decryption requires control component private keys

For Standard Bounties

  • NOT "general best practices" (C.5.4) — this is a concrete code bug, not a missing header or config hardening
  • NOT DoS/resource starvation — this is an authentication bypass
  • Demonstrable with PoC — working Python script proves identical signatures across endpoints
  • Within attacker model — network position between internal components is explicitly modeled
  • Limitation: Direct concrete impact on election integrity/privacy requires chaining with another vulnerability

Recommendation

Submit the URL omission finding as a standard severity report. Frame it as an inter-service authentication bypass that weakens a defense-in-depth layer. The concrete PoC demonstrates the bug is real, even if the direct impact requires chaining. The lack of replay protection (no nonce/timestamp) compounds the severity.

Sweep Approach

  1. Inter-service authentication: Traced the full sign → transmit → verify chain for the SignedRequestFilter across all 9 services
  2. Cryptographic primitives: Reviewed ElGamal implementation, ZKP generation/verification, group element validation, key derivation
  3. Vote lifecycle: Traced vote creation (client JS) → submission → validation → storage → choice codes → confirmation → mixnet → tally
  4. Input validation: Checked all database queries, XSS sanitization, deserialization paths, parameter validation
  5. Authentication: Reviewed extended auth (credential handling, attempt limiting, locking), certificate chain validation, auth token signature
  6. Infrastructure: Checked Docker configs, exposed ports, hardcoded credentials, private key locations
  7. Client-side: Reviewed vote encryption, proof generation, key handling in voting-client-js and cryptolib-js
