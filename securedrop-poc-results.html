SD-001 No Signature Verification on Decrypted Messages Exploitable
redwood/src/decryption.rs:15-33

Vulnerable Code

15impl VerificationHelper for Helper<'_> { 16 fn get_certs( 17 &mut self, 18 _ids: &[sequoia_openpgp::KeyHandle], 19 ) -> sequoia_openpgp::Result<Vec<Cert>> { 20 // we don't care whether messages are signed or not. 21 Ok(Vec::new()) // ← zero certs loaded 22 } 23 24 fn check( 25 &mut self, 26 _structure: MessageStructure, 27 ) -> sequoia_openpgp::Result<()> { 28 // we don't care whether messages are signed or not. 29 Ok(()) // ← unconditional pass 30 } 31}

Attack Scenario

1Attacker intercepts encrypted journalist reply (MITM on Tor circuit or compromised server)
2Replaces ciphertext with a different encrypted message
3Source receives and decrypts the tampered reply silently
4No warning, no error — signature verification is completely absent

Proof

get_certs() returns an empty vector — no certificates are loaded for signature verification. check() returns Ok(()) unconditionally — all signatures pass regardless. The comments in the source code confirm this is deliberate.

SD-002 NullPolicy Fallback Accepts Weak/Revoked/Expired Keys Exploitable
redwood/src/keys.rs:33-65

Vulnerable Code

42let key = cert 43 .keys().secret() 44 .with_policy(crate::STANDARD_POLICY, None) // ← tries standard first 45 .for_storage_encryption() 46 .next(); 47if let Some(key) = key { return Ok(key.key().clone()); } 48 49// No key found, try again with a null policy 50let null = NullPolicy::new(); // ← accepts EVERYTHING 51let key = cert 52 .keys().secret() 53 .with_policy(&null, None) // ← revoked, expired, weak 54 .for_storage_encryption() 55 .next();

What NullPolicy Accepts

  • Revoked keys — a key revoked after compromise still decrypts
  • Expired keys — long-expired keys still work
  • Weak algorithms — 1024-bit RSA, SHA-1, etc.

Attack Scenario

A source's private key is compromised and revoked. The journalist sends a reply encrypted to the source. NullPolicy allows the revoked key to decrypt the reply. The attacker who compromised the key can read it. Revocation provides zero protection.

Contrast

Encryption path (keys_from_cert) correctly filters: .supported().alive().revoked(false). Decryption has none of these checks in the fallback.

SD-031 Reversed Substring Match Returns Wrong Files Exploitable
store.py:165-186

Vulnerable Code

172for rootdir, _, files in os.walk(os.path.realpath(self.__storage_path)): 173 for file_ in files: 174 if file_ in filename: ← REVERSED! checks if disk name is substring of query 175 joined_paths.append(os.path.join(rootdir, file_))

Live Test Results

MATCHExact filename query → correct file returned
MISMATCHCrafted query containing two filenames → returns both (TooManyFilesException or wrong file)

How It Works

The check file_ in filename asks: "is the on-disk filename a substring of the search query?" Since shorter strings are substrings of longer strings, a crafted query containing multiple real filenames matches ALL of them. Should be file_ == filename.

Example

On disk: doc.gz.gpg, msg.gpg. Query: doc.gz.gpg__msg.gpg → matches both files because both are substrings of the query.
